# scripts

Bootstrap, smoke, and developer automation scripts live here.

Operational helper entrypoints:

- `npm run capture:authorized-video`: isolated operator-approved capture helper for login-gated video PPT fallback. Default `--self-test` and `--dry-run` do not open a browser or run FFmpeg. Self-test verifies authorization negative gates and writes a redacted `sharedReceipt` for validation logs. Live capture requires `--run-capture --ack-authorized --approval-id ... --approved-by ... --url ...`; it uses a temporary browser profile, bounded FFmpeg recording, no audio by default, and prints a follow-up handoff command instead of uploading automatically.

Current smoke entrypoints:

- `run-assistant-run-worker-smoke.sh`: non-destructive Linux/deployment-target smoke for the AssistantRun background completion worker queue, workflow registration, and redacted video completion dispatch contract.
- `run-assistant-chat-contract-smoke.sh`: non-destructive local/deployment-target smoke for the user-facing chat contract: ordinary chat stays unrestricted and V3-aware, ReAct fallbacks stay natural-language only, and external callback payloads do not expose internal observability fields.
- `run-newbai-assistant-answer-smoke.sh`: local/deployment-target smoke for NewBai answer-quality handoff. It validates deterministic provider-input supply, the NewBai retrieval-ranking regressions, and, when `PLATFORM_DATABASE_URL` points at a disposable fixture database, the Postgres-backed AssistantRun route. It does not call a real LLM provider or enable `RETRIEVAL_SEARCH_BACKEND=postgres_lexical`.
- `run-newbai-customer-answer-smoke.sh`: deterministic legacy diagnostic for NewBai customer-facing outputs. Its answer-pattern, template-wording and ordinary-route oracles never enter model input; they produce only a `diagnostic_match`, do not prescribe model wording, and are never answer-quality or promotion gates. Fixture mode does not call DataMax, a model provider, PostgreSQL, or static-page/report rendering. Captured provider/live outputs can be supplied later through `NEWBAI_CUSTOMER_ANSWER_RESULTS_JSONL`; because no linked execution-safety receipt exists, those reports record provider/mutation status as unknown rather than inventing a no-call claim. Partial runs must also declare the exact case set with `NEWBAI_CUSTOMER_ANSWER_SELECTED_CASE_IDS`, and undeclared, missing, extra, or duplicate result cases fail closed.
- `run-semantic-supply-ab-smoke.sh`: fail-closed v2 fixture and A/B/C evaluator for knowledge-graph-assisted supply selection. Arm A is the current control, B is graph-only reranking, and C is reranking plus at most two grounded evidence supplements. The bundled 24-case matrix is a synthetic offline retrieval diagnostic covering field aliases, source localization, cross-document evidence, four explicit multi-dataset selected-scope/dual-source localization cases, negative controls, and an explicit eight-case holdout. It does not contain or measure a cross-dataset relation/link snapshot. `--self-test` tests evaluator logic only: it does not call a provider, produce experiment evidence, or authorize a promotion. Real Rust-exported rows must be supplied together with `--runtime-input`, `--a-results`, `--b-results`, and `--c-results`; the evaluator independently recomputes the runtime hashes before trusting producer receipts. `--require-retrieval-metrics` permits `answer_evaluation.status=not_run` and gates retrieval/grounding/permission/contract/latency evidence. `--require-metrics` exercises the answer-receipt v2 diagnostic but intentionally remains non-promotion and exits nonzero until a separately reviewed schema binds every evaluated claim to a visible document/chunk/source locator/retrieval hit and binds the legacy 58 cases through explicit per-case manifests. Reports contain hashes, aggregate counts, metrics, and case ids only, never prompts, answers, or source values.
- `scripts/smoke/semantic-supply-main-live.mjs`: fail-closed scaffolding for a possible future single-arm main-site collector. `--self-test` is deterministic and no-network; `--preflight` performs no writes. Because the current offline result is `retrieval_candidate=null`, this build mechanically rejects every preflight/execute with `live_execution_disabled_without_offline_promotion_candidate` before creating receipt files, authenticating or calling the network. It only reads the repository-owned fixed fixture after rejecting alternate paths and symbolic links. Enabling live later requires a separate code change and fresh review; this scaffold cannot substitute for the promotion gate.

### Semantic supply v2 evidence contracts

`fixtures/semantic-supply-ab/runtime-inputs.jsonl` is physically separate from the evaluator oracle in `cases.jsonl`. Its `semantic-supply-runtime-input.v2` dataset records contain only a shared candidate pool and one shared semantic snapshot per synthetic dataset. Its case records contain only `case_id`, `question`, explicit `selected_scope`, `permission`, and `evaluation_kind`, in addition to schema/record-kind fields. Runtime input validation rejects `expected_*`, `forbidden_*`, `graph_target`, split, prompt, answer, route, intent, message, conversation, system-prompt, and artifact fields. It does not define a dialogue, answer template, route, action, or expected ranking.

For every case, the evaluator combines datasets in selected-scope order and candidates in pool order, then independently computes `question_sha256`, `scope_sha256`, `permission_sha256`, `candidate_snapshot_sha256`, `semantic_snapshot_sha256`, `evaluation_kind_sha256`, and the composed `runtime_input_sha256`. Object hashes use UTF-8 canonical JSON with lexicographically sorted object keys, preserved array order, and no extra whitespace; question and evaluation-kind hashes use their raw UTF-8 strings. A/B/C producer rows are rejected if any reported hash or the exact ordered candidate-id list differs. The four non-retrieval controls use explicit `structured_query`, `structured_row_scan`, `parse_status`, and `ordinary_chat` evaluation kinds; their receipts may not disguise document or graph-reranked hits as guard evidence.

The A/B/C inputs are JSONL with exactly one `semantic-supply-ab-result.v2` row per fixture and arm. A minimal row contains:

- Identity and linkage: `case_id`, `experiment_id`, `arm`, `execution_kind`, `evaluation_kind`, `fixture_sha256`, `runtime_input_sha256`, `candidate_snapshot_sha256`, `semantic_snapshot_sha256`, `scope_sha256`, and `permission_sha256`. Corresponding A/B/C rows must share the experiment and all independently recomputed runtime linkage values and candidate ids. The Rust exporter derives `producer.git_head` with `git rev-parse HEAD`, requires a clean worktree, and records `git_head_source=git_rev_parse_head` plus `worktree_clean=true`; an optional `SEMANTIC_SUPPLY_AB_GIT_HEAD` can only assert equality and cannot supply or override the recorded revision.
- Producer and ranked supply: a Rust fixture-export `producer` receipt, `latency_ms`, `candidate_ids`, `input_candidate_count`, ranked `hits`, `route`, and `artifacts`. In offline rows `route` is exactly a `status=not_run` contract, not an observed model route. Supplement hits also identify the retrieval evidence, document, chunk, and source locator; C may add no more than two hits. A semantic boost or supplement additionally requires the same item's model-visible `summary` or `content_excerpt` to match a document-specific safe alias; locator, payload-filter and manifest metadata cannot establish attribution.
- Grounding: `grounding` plus `grounding_sha256`, including target/resolved node counts, ready/compatible snapshot state, and zero inferred, unresolved, stale, hidden, or unresolvable node use.
- Immutable component receipt: `contract` hashes for question, system prompt, answer policy, provider config, selected scope, permission, evaluation kind, runtime input, action catalog, route, model-visible evidence, and provider input; `provider_input_bytes`; provider call/retry counts; workflow/artifact/report/template/static-page deltas; and `same_run_off_path_self_consistency`. The latter is a same-execution implementation check, not an independently captured frozen feature-off baseline.
- Offline answer state: `answer_evaluation: {"status":"not_run","reason":"..."}`. An offline row must not contain `answer`, and its citations must be empty. Such rows can become `retrieval_ready` only.

Each fixture declares `selected_scope.selected_dataset_keys` and the exact safe `allowed_evidence_classes: ["confirmed", "observed"]`. Single-dataset cases select only their `dataset_key`; multi-dataset selected-scope cases select at least two explicit synthetic dataset keys. Those four cases verify authorized dual-source localization only; they do not assert or score an inter-dataset relation. These fields, `expected_sources`, and the other supply-quality `expected_*` values are evaluator oracle data. A runtime exporter may execute and hash the declared request scope, enforce the production confirmed/observed safety rule independently, and record observed output. It must not use oracle fields to construct candidate order, expected hits, ranks, grounding outcomes, model intent, route, action, answer, or pass/fail results.

The optional `semantic-supply-answer-evaluation.v2` object is a schema/evaluator diagnostic only. It can compare declared route objects for a separately captured full-answer receipt, but the bundled offline exporter measures only route-not-run consistency and never route parity. Even for a full-answer receipt, v2 does not carry independently recomputable claim-to-document/chunk/source-locator/retrieval-hit records. Its NewBai 8/8, document-quality 11/11 and regression summary integers are informational and do not merge or bind the separate legacy 35+12+11 suites into the 24-case A/B/C receipt.

Consequently v2 is deliberately non-promotion: `--require-metrics` remains fail-closed even when a syntactically valid v2 receipt is supplied. A future promotion-capable contract requires a new reviewed runner/schema with per-case source binding, explicit legacy-suite case manifests, and an independently captured feature-off baseline. Environment equivalents remain `SEMANTIC_SUPPLY_RUNTIME_INPUT`, `SEMANTIC_SUPPLY_A_RESULTS`, `SEMANTIC_SUPPLY_B_RESULTS`, `SEMANTIC_SUPPLY_C_RESULTS`, `SEMANTIC_SUPPLY_ANSWER_RECEIPT`, and `SEMANTIC_SUPPLY_AB_OUTPUT_DIR`; all three result variables must be set together and must have an independent runtime input.

### Semantic supply main-site live harness

This harness never orchestrates dialogue, intent, answer structure, conclusions, wording, routes or actions. Its request contains the unchanged fixture prompt and the explicit selected dataset scope only. It observes the model's own answer and any provider, route, workflow, artifact, evidence and citation signals; it does not prescribe them.

Safe local checks:

```bash
node scripts/smoke/semantic-supply-main-live.mjs --self-test --pretty

node scripts/smoke/semantic-supply-main-live.mjs --preflight \
  --ack-controlled-live --approval-id APPROVAL-ID --arm A \
  --base-url https://v3.example.invalid --dataset-id 00000000-0000-4000-8000-000000000000 --pretty
```

Authentication is environment-only: either `SEMANTIC_SUPPLY_MAIN_SESSION_COOKIE`, or both `SEMANTIC_SUPPLY_MAIN_AUTH_EMAIL` and `SEMANTIC_SUPPLY_MAIN_LOCAL_KEY`. Every preflight/execute also requires `SEMANTIC_SUPPLY_MAIN_APPROVED_IDENTITY_SHA256`; an existing-cookie run may additionally use `SEMANTIC_SUPPLY_MAIN_SECRET_BINDING_IDS`. Do not put cookies, local keys, provider keys or raw credentials on the command line, in Git, or in shared receipts.

The future execute shape is shown only for contract review; it is mechanically disabled in this build:

```bash
node scripts/smoke/semantic-supply-main-live.mjs --execute \
  --ack-controlled-live --approval-id APPROVAL-ID --arm A \
  --base-url https://v3.example.invalid --dataset-id 00000000-0000-4000-8000-000000000000 \
  --case-ids newbai-customer-001 --output-dir target/semantic-supply-main-live
```

Running that command now fails before network, authentication, receipt creation or filesystem writes. If a later clean-commit offline receipt has a non-null candidate, the hard disable must be removed in a separately reviewed change before any controlled-live approval is usable. The dormant contract is limited to one main-site stream POST attempt per selected registered case and then read-only detail polling; it does not retry a provider/stream request, call an external channel, create or edit business datasets/assets, change feature flags, or auto-delete cleanup data. The private raw receipt and private no-auto-delete cleanup manifest are separate 0600 artifacts; the redacted summary only records their contract/status. A self-test, preflight, or single-arm receipt is never decision-eligible by itself.

It registers a public or loopback video fixture through `/v1/external/channels/{connection_id}/documents/parse`, sends a scoped `/events` message that explicitly asks to extract PPT/slides/courseware already shown in the video, polls the assistant-run reply, and validates the third-party video extraction card plus optional PPTX/Markdown/manifest downloads. Use `-- --self-test` for the deterministic offline reply-surface contract plus minimal PPTX/Markdown validation. Use `-- --preflight` to validate third-party context, fixture/source shape, trigger payload, redaction, and live write scope without network calls; live mode still requires an approved inbound bearer.
- `npm run test:pure-third-party-guide-html`: checks the current public HTML/Markdown integration guides and their published `/external-integrations/...` copies.
